## New findings

### N1 — HIGH — The B5 fix reached only one of its two call sites

**File:** `kidney-backend/app/services/exchange_graph_service.py:149`

`check_dsa` gained a `donor_typed_loci` parameter so an antibody against a locus the donor
was never typed for is flagged rather than silently treated as a negative.
`match_pipeline.py:255` passes it. **`exchange_graph_service.py:149` does not:**

```python
dsa_result = check_dsa(patient_antibodies, donor_hla_antigens)   # no donor_typed_loci
```

Pool entry requires complete typing only at **A, B and DRB1** — DQ, DP and C are not
required. So a recipient with a strong anti-DQ antibody, paired against a donor with no DQ
typing, produces a **compatible exchange edge with no review signal at all**.

**Reproduction (from `kidney-backend/`, `PYTHONPATH=.`):**

```python
from app.services.exchange_graph_service import evaluate_pair_edge
from app.services.dsa_service import PatientAntibody, check_dsa

r = evaluate_pair_edge(
    patient_typing={"A":["01","03"], "B":["07","08"], "DRB1":["01","04"]},
    donor_typing  ={"A":["01","03"], "B":["07","15"], "DRB1":["01","04"]},
    patient_antibodies=[PatientAntibody(antigen="DQ7", mfi=9000.0)],
    donor_hla_antigens=["A1","A3","B7","B15","DR1","DR4"],   # no DQ typed
    patient_blood_type="A", donor_blood_type="A",
)
print(r.is_compatible, r.dsa_result.requires_review, r.dsa_result.untyped_locus_antibodies)
```

**Actual output:**

```
EXCHANGE EDGE — recipient has anti-DQ7 MFI 9000, donor has no DQ typing
  is_compatible        : True
  dsa requires_review  : False
  untyped_locus flags  : []

Same antibody through the main pipeline's call (donor_typed_loci supplied):
  requires_review      : True
  untyped_locus flags  : ['DQ7']
```

Identical clinical data, opposite answers, depending on which path evaluates it. The
exchange engine is the path that *proposes* transplants to coordinators, so it is the one
where a silent false negative travels furthest.

**Fix:** thread the donor's typed loci through `load_exchange_pool` → `build_exchange_graph`
→ `evaluate_pair_edge` → `check_dsa`. Then decide what the flag does — that is **Question 7**
on the doctors' sheet, so build the detection now and gate the behaviour on their answer.
Add a test asserting the two paths agree on identical inputs; that test is what stops this
class of drift recurring.

### N2 — MEDIUM-HIGH — The report claims a DSA was detected when none was

**Files:** `kidney-backend/app/services/report_outcome_service.py:217`,
`kidney-backend/app/reference_data/report_outcome.py:76`

`requires_review` correctly became true for unmapped and untyped-locus antibodies:

```python
requires_review = (
    any(match.severity != DSA_HALTING_SEVERITY for match in matches)
    or bool(unmapped_antibodies)
    or bool(untyped_locus_antibodies)
)
```

But `build_report_outcome` still keys the flag off `requires_review` alone, and that flag's
label is **"Donor-specific antibody detected"**. With zero matches, the report now says:

```
VERDICT : Proceed with Caution
FLAGS   : [('dsa_requires_review', 'Donor-specific antibody detected'),
           ('unmapped_antibody',   'Antibody could not be matched against donor typing')]
```

No donor-specific antibody was detected. One could not be excluded. Those are different
clinical statements, and the first one is wrong.

This is the mirror image of B2: instead of hiding a real DSA, the system now asserts one
that was never found. The two correctly-worded flags beside it make the false one more
confusing, not less — a clinician reads three flags and has to work out which is real.

**Fix:** gate `REVIEW_FLAG_DSA_REQUIRES_REVIEW` on `dsa_result["matches"]` being non-empty,
not on `requires_review`. The unmapped and untyped-locus cases already carry their own
accurate flags and need nothing more.

### N3 — LOW-MEDIUM — `ocr-service` has no CI workflow

**Files:** `.github/workflows/`

Four workflows exist. `pii-scan.yml` and `constants-sync.yml` run unfiltered on every
push and PR — good. But `backend.yml` and `frontend.yml` are path-filtered to
`kidney-backend/**` and `kidney-frontend/**`, and **there is no workflow for `ocr-service`
at all.**

So `ocr-service`'s 78 tests and its own ruff config never run in CI, and a change confined
to `ocr-service/**`, `Caddyfile`, `docker-compose.prod.yml`, `scripts/` or `docs/` triggers
only the two guard workflows.

This matters more than it looks: `ocr-service/app/llm/prompts.py:189` is what instructs the
model to read the **Sero** column and not "Allele Equiv" — the upstream half of the B2
safety story. A regression there would produce exactly the allele-level antigens B2's
validation now rejects, and nothing in CI would catch it.

**Fix:** add `ocr-service.yml` mirroring `backend.yml` (ruff + pytest, no Postgres service
needed). Add the repo-root paths to the trigger filters, or drop the filters.

### N4 — LOW — The access log can carry query strings

**Files:** `kidney-backend/app/core/logging.py`, `kidney-backend/app/core/request_logging.py`

`logging.py`'s docstring states a hard rule, and `RequestIdMiddleware` honours it exactly —
method, path, status, duration, never the body or query string.

But `configure_logging` also routes `uvicorn.access` through the same handler, and uvicorn's
access log records the full request line **including the query string**. Nothing in the app
takes a clinical query parameter today (every one is a UUID, int or enum), so nothing leaks
now. The invariant just is not actually enforced — the first route that accepts
`?nic=` or `?antigen=` breaks it silently.

**Fix:** either pass `access_log=False` to uvicorn (the middleware already covers it) or set
the `uvicorn.access` logger to `WARNING`. One line, and the docstring becomes true.

is fine. Just be aware that the verdict a doctor actually sees for missing typing is the 422
message, not the report, so that message is the one worth getting right.
